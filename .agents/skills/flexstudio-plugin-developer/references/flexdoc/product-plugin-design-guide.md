# 产品级插件设计指导

本页用于设计、重构和评审连接外部服务、设备或协议的 FlexStudio 产品级插件。它说明如何组织产品边界、状态和 Unit 体验；精确 API、manifest 字段和状态通道 wire 契约仍以 [插件系统概览](./overview.md)、[后端运行时](./backend-runtime.md)、[插件依赖 API](./dependency-api.md)、[Unit 定义](./unit-definitions.md) 与 [前端桥接](./frontend-bridge.md) 为准。

UI 组件、主题和可访问性规则以 [插件 UI/UX 设计指导](./ui-ux-guidelines.md) 为准。本页不记录某个外部协议的请求字段、重试数值或产品功能清单；这些内容应留在对应产品设计和协议文档中。

## 先确定产品边界

默认优先单一产品插件。若外部连接、认证、状态、Unit、编辑器和设置页只服务于一个产品，它们应由同一插件拥有，避免把连接生命周期和用户体验拆到不同进程后再转发状态。

只有同时满足以下条件时才拆分可复用 Essentials：

- 至少两个相互独立的产品确实复用同一协议、认证、连接或状态模型；
- Provider 能提供与任何单一 Flexbar UI 无关、版本稳定的业务契约；
- 团队愿意维护 Provider/Consumer 的版本兼容性、依赖声明与跨插件集成测试。

即使存在 Essentials，也不要把 Library、Unit 外观、编辑器、预设或产品快捷交互放进它。产品插件仍负责完整的用户可见体验。

## 以控制模型和真实 Catalog 组织能力

不要让 UI、Unit 和设备事件直接依赖外部协议的方法名与原始参数。先定义稳定的控制模型，分别描述可执行控制、当前状态、目标选项和不可用原因；协议适配层负责把原始请求与事件映射到该模型。

Catalog 是外部系统当前可选目标的权威来源，例如设备、场景、输入、账户或项目。功能编辑器必须从真实 Catalog 填充选择器，并在连接或数据不可用时保留已保存目标、明确标记为不可用或待配置。禁止用静态示例项、假目标或占位列表模拟真实选择。

Unit 数据只保存稳定的控制 ID、目标 ID 和必要的模式，不缓存完整外部对象。目标消失时保留绑定并显示 warning；不得静默替换为默认目标或其他动作。

## 一个 Unit 只完成一个任务

一个 Unit 类型应对应用户能理解的明确任务，例如“切换目标”“静音输入”或“设置输入音量”。不要提供一个泛化 Unit，再用 action 下拉框把不相关功能隐藏在其中。

- 无参数动作不应有功能编辑器。
- 有目标的 Unit 只显示该任务需要的专属选择器。
- 数值型 Unit 使用语义正确的 slider、stepper 或输入，并明确范围、单位与更新时机。
- 低频高级命令可以是独立的 Advanced Unit，但不能成为通用原始协议调用入口。
- `cycled`、`button-group` 与 slider 的运行时状态、默认项和可选项必须来自同一控制模型，不得借它们实现无关动作选择。

改变 Unit ID、控制 ID 或数据结构前，先定义迁移策略。发布过的插件通过 `migrateUnit()` 显式迁移；无法可靠映射时保留原数据并将 Unit 标记为待配置，绝不能用隐式默认值改变用户原有行为。

Unit 数据应使用按 Unit 类型和模式区分的闭合联合，并对允许字段做精确校验。不要接受任意额外字段、遗留 action 对象或原始请求参数；否则旧数据和拼写错误会悄悄进入新模型。

`hasFunctionEditor` 是产品目录契约，不是纯 UI 细节。所有需要选择目标、模式或参数的 Unit 都必须在生成的 definitions 中声明编辑器；测试应从真实 definitions 断言该集合，而不是只直接挂载编辑器组件。

危险或不可逆的 click 动作需要默认长按确认时，在 Unit definition 中声明宿主拥有的 `defaultActivation: { mode: 'hold', holdDurationMs }`。该默认值只应用于新建 Unit，用户之后可以在宿主中覆盖；插件仍只处理 canonical activation。不要在插件中监听 pressed/released、自行启动长按计时器，也不要把宿主 activation 配置混入业务 `defaultData`。

`cycled` Unit 可能投影的每个 function ID 都必须形成闭合集合，并在 definition 与全部 locale 中声明。外部系统返回开放枚举时，应归一化到已声明状态或稳定的 `unknown`，不能把任意外部字符串直接当 function ID。

## 库入口与转换式 Unit

当产品里同一类对象在选好之前不知道该用哪种原生 Unit 时（例如智能家居“控件”可能是开关、滑块、选项、数值或文本），不要在库里摆出所有类型：

1. 库里只放一个占位定义（例如 `Control`），其余定义标记 `visibleInLibrary: false` 保留为转换目标和旧项目兼容。
2. 编辑器用“设备 → 控件”两步选择，由插件根据所选控件决定目标类型，并用 `convertUnit({ unitId, data, appearance, icon })` 一次转换并绑定。之后更换控件走同一个调用。
3. 面板生成、单个控件和物理输入功能共用同一个“控件 → Unit 数据”映射，保证同一个控件在任何入口得到相同的服务、范围和状态路径。
4. 控件按含义命名并显示当前值，不要按 Unit 类型命名，也不要让同一设备出现多行相同的名字。

写入失败（格式不合法、目标不存在）会以 `Error` 返回，编辑器必须显示这些错误。

## 用一个状态存储完成双向同步

外部变化和设备操作必须汇合到同一个状态存储：

```text
外部事件 -> 状态存储 -> 所有受影响的 loaded Units -> 设备显示
设备输入 -> 标准化命令 -> 外部请求 -> 外部确认事件 -> 状态存储 -> 所有受影响的 loaded Units
```

不要仅更新发起动作的 Unit，也不要在外部请求返回成功后乐观地永久展示新状态。只有外部确认事件或有目的的领域刷新写入状态存储后，才向所有观察同一控制、目标或领域的 loaded Units 投影运行时状态。

为 loaded Units 建立按状态域、控制 ID 和目标 ID 的索引。一次外部变化必须更新全部相关 Unit。外部事件不完整、丢失或只表示集合失效时，可以触发限流的全量或领域刷新；禁止用固定 interval、长轮询或全局事件总线伪造实时同步。

连接状态与业务快照的新鲜度必须分离：连接管理器拥有传输状态，状态存储拥有 `stale` / 同步中的业务数据。缓存存在不表示连接可执行；局部刷新失败也不应把有效连接误判为断开。执行动作前检查连接可用性与所需状态域的新鲜度。

领域刷新与外部事件可能并发到达。刷新结果不得覆盖刷新期间已确认的较新事件；状态存储应使用 revision、generation 或等价合并策略，并合并同一领域的失效刷新请求。配置是否已保存也只是持久化事实，不能被当作连接状态、快照新鲜度或目标可用性的替代指标。

完整 hydrate 同样必须参与 revision/generation 合并。hydrate 期间到达的外部事件不能被较早查询结果回滚；切换连接世代时，旧 hydrate 必须失效，新连接的快照完成前应立即标记为 stale，禁止用上一连接的目标执行命令。

集合领域和派生领域要共享明确的所有权。例如设备列表与设备详情、场景列表与场景项不能各自用互不相关的 generation 覆盖对方。Owner 刷新应使旧派生刷新失效；较新的派生刷新不能取消仍必要的 Owner 刷新。

事件 payload 常常只包含部分字段。Reducer 应按实际出现字段做 patch，不能用缺省值覆盖已有状态。异步刷新失败必须被捕获并进入受控 stale/error 状态；dispose 后不得继续发起刷新或发布快照。

命令确认应匹配事件类型、状态域、目标身份和期望状态。不能仅因“同域发生变化且当前值恰好相同”就取消兜底刷新；一个确认事件至多消费一条对应的 pending 命令。事件缺失时，兜底刷新必须查询该命令真正依赖的权威状态。

持续的跨插件状态使用 Dependency State Channel；同一插件后端到 iframe 的持续状态使用 Renderer State Channel。一次性命令或查询才使用 dependency API 或 `backendRpc()`。状态通道只承载最新 snapshot 或可重建 delta，不传秘密、不充当审计日志，并正确处理 epoch、revision、`unavailable` 与重同步。

## 连接、设置和错误体验

连接型产品应有唯一的长生命周期连接所有者。保存新配置、断线重连、插件加载和卸载都通过同一连接生命周期处理，避免 Unit 或 iframe 私自创建长期客户端。慢连接、发现或全量同步不能阻塞 `onLoad()`；先注册定义、RPC 和状态通道，再在后台执行同步。

网络或 socket 建立不等于产品已经可用。进入可执行状态前，连接管理器必须完成产品所需的认证、版本协商或最小健康检查，并以安全、可操作的错误结果表示失败。替换已在使用的连接配置时，先隔离验证候选连接；仅在候选满足这些后置条件后才原子切换并持久化。候选失败必须保留旧的可用连接与配置。

候选连接从验证完成到提交之间也可能断开。准备阶段就应监听候选存活状态，提交时再次检查 token 与连接状态；成功提交要推进单调连接世代，使旧异步任务无法向新连接发布数据。

配置与 secret 的更新要按事务处理。任一步持久化失败都应返回稳定错误并补偿已写入的数据，同时保留旧连接；不得先覆盖配置，再把进入重连状态包装成“连接成功”。

设置页围绕高频用户任务组织：连接、授权、保存、当前状态和可操作的失败原因。只暴露用户真正拥有的设置；实现内部的超时、重试、TLS 或缓存策略不应因为“可以配置”就占据主表单。首次配置可使用简短引导，已配置状态优先显示最短恢复路径。

“保存并连接”必须建立生产连接并完成最小状态基线，不得把只验证候选参数的测试结果称为连接成功。显式用户动作可以显示具体 snackbar；自动重连和后台同步不应刷屏。密码、token 和 OAuth 凭据必须使用 `hostApi.secrets`，输入框保持只写语义，日志、错误、状态与 RPC 不得泄露内容。

Snackbar 是显式动作的附属反馈，不是动作结果本身。通知 API 失败不得把已经成功的连接改写成失败，也不得递归触发第二条错误通知。初始加载和后台失败应使用短小、可操作的内联状态，不主动弹 snackbar。

断线、权限缺失、认证失败、超时、目标缺失和状态过期都应有稳定、可恢复的状态。未连接或状态陈旧的 Unit 进入 warning 或 disabled，同时保留其绑定和解释；不要崩溃、循环重启或静默执行其他目标。

短时异步动作执行期间，Unit 应进入 `loading` 运行时状态以显示居中 spinner 并阻断重复设备交互；动作结束后必须显式恢复为 `enabled`、`warning` 或 `disabled`。显式设备动作可以在发起设备上显示结果 snackbar，但通知失败不得覆盖真实动作结果。

## 界面、图标与本地化

配置页与功能编辑器使用 Vuetify 3 的紧凑 `solo-filled` 输入、`tonal` 按钮与小型状态 chip；默认使用 FlexStudio `primary`，明确产品品牌仅作局部 accent。避免 hero、营销式说明、重复标题、卡片套卡片和长期占据页面的诊断面板。

编辑器只显示当前 Unit 需要的字段，窄 iframe 下字段、chip、按钮和文本必须可换行、截断或重排。icon-only 操作必须有 tooltip 或 aria label。所有用户可见文本、错误和断线状态都走 i18n，并同步维护产品支持的全部 locale。

枚举标签与外部动态名称必须分开处理。模式、状态和动作名称走 i18n；设备名、场景名、账户名等外部名称应原样显示，不得拼成翻译键。

编辑器必须同时检查 iframe bridge readiness 与后端连接状态。断线时保留缓存选项但禁用 live 控件。异步加载要使用 generation 或 captured ID，只允许最新请求更新页面；旧请求的成功或失败不能覆盖新 Unit 的状态。

本地草稿与异步宿主回显要隔离。复杂文本或 JSON 应在 blur、显式提交或受控 debounce 后写入，并处理保存拒绝；宿主返回的旧值不能覆盖用户正在编辑的草稿。

选择 MDI 图标时，除检查当前前端字体包外，还要验证 Host/设备端映射与真实设备运行时。前端能显示图标不等于设备端可用。

## 验证与发布

按完整闭环而不是孤立 mapper 设计测试：

- 控制模型、命令映射、真实 Catalog、事件归一化和状态新鲜度；
- 外部变化更新所有相关 loaded Units；
- 设备操作经外部确认或受控兜底刷新后更新所有相关 Unit；
- 断线、重连、权限错误、目标缺失、状态通道重放/重同步和卸载；
- 编辑器专属字段、无参数动作无编辑器、i18n、错误状态与窄布局；
- deferred Promise 驱动的连接切换、hydrate/事件乱序、同域与依赖域刷新竞态；
- 生成 definitions 与编辑器挂接、全部 function ID、闭合数据联合之间的契约；
- 使用真实后端 DTO 和真实 locale 的 UI 测试，以及至少一层真实 Vuetify 挂载 smoke test；
- snackbar、保存和加载 API 拒绝时不产生重复通知、未处理 rejection 或旧结果覆盖；
- MDI 图标的设备运行时检查，以及目标平台的构建、打包和安装验证。

显式“测试”或“保存并连接”动作应断言真实协议后置条件、生产连接切换和可验证的 snackbar 结果；仅验证 TCP/WebSocket 打开或 RPC 成功不足以证明产品已连接。

对 Windows/macOS universal 产品，构建与打包验证必须覆盖 manifest 声明的平台；无法在某个平台交付时，先收窄声明并报告，不要静默降级。源改动先在相应子仓库提交，再由顶层元仓库记录 gitlink；不要提交 `dist`、`node_modules`、release 包或临时产物。

## 评审反模式

- 仅因历史惯性拆分 Essentials，或把产品 UI 放入 Essentials；
- 泛化 action 下拉框、假 Catalog、隐式目标回退；
- 把成功请求当作持久状态确认，或只更新点击的 Unit；
- 用轮询、长轮询或全局 bus 代替受控状态通道与领域刷新；
- 混淆连接可用性和快照新鲜度；
- 连接切换后继续使用上一连接的非 stale 快照；
- 用同域任意变化确认命令，或让一个事件同时确认多条 pending 命令；
- 让完整 hydrate、集合刷新和派生刷新用互不协调的 generation 覆盖彼此；
- 把动态外部名称当 i18n key，或让旧异步请求覆盖当前编辑器；
- 只直接挂载编辑器测试，却不验证 definitions 是否真正声明 `hasFunctionEditor`；
- 把秘密写入普通配置、日志、错误或状态；
- 把内部调参暴露为默认表单、把诊断和说明压过常用任务；
- 未验证真实设备图标或平台包，就宣称跨平台可用。
